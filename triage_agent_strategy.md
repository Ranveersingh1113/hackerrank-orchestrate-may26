# Multi-Domain Support Triage Agent — Strategic Research Report
*HackerRank Orchestrate (May 1–2, 2026) — Build Guidance & Differentiators*

---

## 1. The Hackathon Problem in Concrete Terms

The challenge (`interviewstreet/hackerrank-orchestrate-may26`) is a 24-hour solo build. You must ship a **terminal-based AI agent** that triages real support tickets across three product ecosystems — **HackerRank Support, Claude Help Center, and Visa Support** — using **only the provided support corpus** shipped in the repo (no scraping, no outside knowledge).

**Input schema (per CSV row):** `issue` (ticket body), `subject` (may be blank/noisy/misleading), `company` (`HackerRank` | `Claude` | `Visa` | `None`).

**Required outputs:**
- `status` ∈ {`replied`, `escalated`}
- `product_area` (free-form domain category)
- `response` (user-facing answer grounded in the corpus)
- `justification` (concise reasoning trace)
- `request_type` ∈ {`product_issue`, `feature_request`, `bug`, `invalid`}

**Mandatory behaviors called out in `problem_statement.md`:**
- Identify request type, classify product area, assess urgency/risk.
- Decide reply vs. escalate; retrieve relevant docs; generate grounded responses.
- Handle multi-request rows, irrelevant/misleading/malicious text, and rows where `company=None` (cross-domain inference required).
- Avoid unsupported claims or hallucinated policies.
- Escalate sensitive cases (billing, fraud, account access, assessments, permissions, bugs).

**Submission artifacts:** zipped `code/` directory, populated `output.csv`, and a `log.txt` chat transcript auto-generated by the `AGENTS.md` instructions (any modern coding tool — Cursor, Claude Code, Codex, Gemini CLI, Copilot — appends turns there). An AI Judge interview follows submission.

The repo also references `evalutation_criteria.md` (note the typo) for the rubric. The contest page and external write-ups indicate scoring weights innovation, functionality, code quality, completeness, and the candidate's articulation of design choices to the AI Judge — so **architectural defensibility matters as much as raw accuracy**.

The three corpora differ sharply in shape and risk profile:
- **HackerRank Support** — assessments/integrations/proctoring/billing/candidate vs. recruiter perspectives; many "how-to" articles plus release-note style content (e.g., the January 2026 release notes covering AI Fluency, Code Repo, integrity signals).
- **Claude Help Center (support.claude.com/en/)** — usage limits, billing tiers, MCP, Claude Code, Projects, safety, account & login. Heavy on policy-like content where hallucinated rate limits or pricing would be a fatal evaluation error.
- **Visa Support (visa.co.in/support.html)** — region-specific (India), card-related, fraud, lost/stolen card, dispute & chargeback, merchant categories. **The highest-stakes domain**: fraud and disputes are the canonical "must-escalate" cases.

## 2. Existing Implementations of Support Triage Agents

### 2.1 Production case studies worth stealing patterns from

**Wayfair "Wilma" (Oct 2025, ZenML LLMOps DB).** Event-driven LangGraph pipeline: ticket webhook → Pub/Sub → LangGraph graph orchestrating a ReAct sub-agent with BigQuery access. They reported 93% accuracy on question type (across 81 categories) vs. 75% human baseline; 98% on language detection; 88% on supplier ID extraction. Critically, Wayfair migrated **from a pure agentic system to a hybrid workflow + embedded agent** — deterministic outer ordering, freedom for the agent only inside specific reformulation/query nodes. This is the single most important lesson: **deterministic outer skeleton, agentic inner loop** outperforms either extreme.

**Scalekit / Zendesk + Notion + Slack triage (2025).** Five-stage pipeline: **Classify → Search KB → Route → Update → Confirm**. Categories = {billing, bug, feature request, how-to, account issue}; severity P0–P3. Bugs/how-tos/account issues trigger KB search; billing/feature requests skip retrieval and route directly to humans. Almost identical shape to what the hackathon needs.

**Open Ticket AI (otai-* plugins, OTOBO/Zammad/Freshdesk/Zendesk).** A pipe-based, YAML-configured engine where each pipe checks conditions, calls LLMs, or interacts with a ticket system. Useful as a mental model for declarative pipeline design.

**Analytics Vidhya "Sentiment-Driven Ticket Triage."** Demonstrates the simplest baseline: HuggingFace sequence classifier + LLM-generated reply. Sentiment tilts urgency/priority but doesn't replace topical classification.

### 2.2 Framework landscape

- **LangGraph** is the dominant choice in 2025–26 production triage stacks (Wayfair, Scalekit, Klarna, Replit). Its primitives — typed state, conditional edges, checkpointing, human-in-the-loop, durable execution — map cleanly to "classify → retrieve → answer | escalate."
- **CrewAI** is more popular for multi-role role-play agents than for triage. It abstracts more, which hurts when you need fine-grained escalation control.
- **LlamaIndex + Haystack** dominate the retrieval layer; either can sit underneath LangGraph.
- **PydanticAI** is gaining traction for type-safe structured outputs — directly useful here because the output schema is fixed (5 fields, 2 enum-constrained).
- **DSPy** is worth mentioning for self-optimizing prompts on the labeled `sample_support_issues.csv`, but its compile loop is too slow for a 24-hour build.

For a 24-hour hackathon, the pragmatic stack is: **Python + LangGraph (or a hand-rolled state machine) + Pydantic for output validation + LLM Wiki pre-compiled knowledge layer + qmd for search + an LLM (Claude Sonnet 4.x or GPT-5) + Rich/Textual for the terminal UX.**

## 3. RAG for Support Corpora — The LLM Wiki Approach

> **Key decision:** Instead of standard RAG (chunk raw HTML → embed → retrieve fragments at query time), this project uses **Karpathy's LLM Wiki pattern** as the knowledge layer. The corpus is fixed and known upfront — ideal for a one-time pre-compilation that pays dividends on every ticket processed.

### 3.1 What LLM Wiki is (and why it fits here)

Andrej Karpathy published the LLM Wiki pattern as a GitHub Gist in April 2026 (5,000+ stars within days). The core insight:

> *"RAG retrieves fragments and synthesizes on every query. The LLM Wiki compiles knowledge once and keeps it current — not re-derived on every query."*

Instead of retrieving raw document fragments at query time and asking the LLM to synthesize them on the fly, you run a **one-time ingest pass** where an LLM reads every article in the corpus and writes structured, interlinked markdown wiki pages. Each subsequent ticket query reads 1–3 pre-compiled pages rather than stitching together raw chunks — faster, more grounded, and with cross-article contradictions already flagged.

This is **not a replacement for the triage graph, classification, or escalation logic** — it only replaces the retrieval layer.

### 3.2 Three-layer architecture

The LLM Wiki pattern uses three layers, mapped to the hackathon context:

**`raw/`** — immutable scraped HTML/markdown from the three help centers. The LLM reads from these but never modifies them. Source of truth.

**`wiki/`** — one subdirectory per domain (`hackerrank/`, `claude/`, `visa/`), each containing LLM-generated markdown pages. One page per article or logical topic cluster. Each page has:
- Extracted key claims (grounded in source text)
- Source URL citation
- Cross-references to related pages (e.g., `claude/billing.md` links to `claude/usage_limits.md`)
- Contradictions with other pages flagged inline
- Escalation signals noted (e.g., "fraud/dispute mentions in this article → always escalate")

**`AGENTS.md` (schema)** — the hackathon already requires this file. It doubles as the LLM Wiki schema: it tells the ingest agent how to structure pages, what per-domain conventions to follow, and what escalation signals to tag. You co-evolve this with the agent during the ingest phase.

### 3.3 Two special navigation files

**`wiki/{domain}/index.md`** — content-oriented catalog. Every wiki page listed with a link, a one-line summary, and metadata (article source, last updated, escalation risk level). The triage agent reads this first on every ticket to find the relevant 1–3 pages, then drills in. No embedding search needed at this stage — the index is small enough for a direct LLM read. This replaces the BM25 first-pass filter.

**`log.md`** — append-only chronological record of ingest passes and lint runs. Maps directly to the required `log.txt` submission artifact. Use consistent prefixes: `## [2026-05-01] ingest | HackerRank | January 2026 Release Notes` so it's grep-able.

### 3.4 The three operations

**Ingest (done once, hours 0–3).** Drop each corpus article into `raw/`, run the ingest agent:
1. LLM reads the article.
2. Writes a structured wiki page in `wiki/{domain}/`.
3. Updates `wiki/{domain}/index.md`.
4. Updates relevant cross-referenced pages (e.g., a new billing article might update `claude/billing.md` and touch `claude/usage_limits.md`).
5. Appends to `log.md`.

Use Claude Haiku or GPT-4o-mini for ingest to keep cost low — the hard synthesis work is cheap classification and extraction, not complex reasoning. Budget ~1–2 hours of run time for the full corpus.

**Query (runs on every ticket).** The triage agent:
1. Reads `wiki/{domain}/index.md` (or all three if `company=None`).
2. Identifies 1–3 relevant wiki pages.
3. Reads those pages in full.
4. Grounds its `response` and `justification` in the page content — not raw fragments.

**Lint (optional, if time permits).** Ask the LLM to health-check the wiki: find contradictions between pages, orphan pages with no inbound links, escalation signals missing tags, stale claims. Especially valuable for the Visa corpus where policy details are high-stakes.

### 3.5 Search layer: qmd

When the `index.md` lookup is insufficient (e.g., `company=None` cross-domain queries, ambiguous tickets), use **qmd** — Tobi Lutke's (Shopify CEO) local search engine for markdown files. Karpathy explicitly recommends it as the search layer for LLM Wikis.

qmd provides:
- Hybrid BM25 / vector search over markdown files
- LLM re-ranking of results
- CLI interface (agent can shell out to it: `qmd search "chargeback dispute timeline"`)
- MCP server interface (agent can use it as a native tool)
- Fully on-device, no external dependencies

This **replaces the FAISS + BM25Retriever + cross-encoder reranker** stack from a standard RAG pipeline. Simpler to set up, same retrieval quality, and it operates over the pre-compiled wiki pages rather than raw chunks — so every hit is a structured, cited page, not a raw 400-token fragment.

### 3.6 Chunking strategy (only if wiki ingest is skipped)

If the ingest phase runs long and you fall back to standard RAG as a backup:
- Recursive character splitting with separators tuned for help-center HTML (`\n## `, `\n### `, `\n\n`, `\n`, ` `).
- Chunk size: 400–800 tokens with 10–20% overlap. Smaller (256) for FAQ-style Visa pages; larger (800) for HackerRank step-by-step articles.
- Preserve heading breadcrumbs — prepend the article title and section path to each chunk's text.
- Metadata per chunk: `{domain, article_id, article_url, section, last_updated}`. Filter by `domain` at query time.
- Index per domain (three separate FAISS/Chroma indexes) to prevent cross-domain contamination.

### 3.7 Anti-hallucination: the "say sorry / show sources" pattern

Whether using LLM Wiki or fallback RAG, the same rule applies: **if no retrieved page/chunk passes a relevance threshold, refuse to generate a substantive answer and escalate.** This maps cleanly to the contest's `escalated` status and is the single most effective anti-hallucination pattern. With LLM Wiki, the wiki page itself contains source citations — so the `justification` field can name specific pages and URLs, which the AI Judge can verify is not hallucinated.

## 4. Classification, Routing, and the Reply-vs-Escalate Decision

### 4.1 Building the classifiers

Two classification heads are needed:

1. **`request_type`** ∈ {`product_issue`, `feature_request`, `bug`, `invalid`} — straightforward 4-way LLM classification with few-shot examples drawn from `sample_support_issues.csv`.
2. **`product_area`** — open-ended but should snap to a closed taxonomy derived from the wiki index headings. Pre-defined areas per domain:
   - HackerRank: *Assessments, Code Repo, Integrations, Billing, Proctoring, Account*
   - Claude: *Usage Limits, Billing, Claude Code, Projects, MCP, Account & Login*
   - Visa: *Lost/Stolen, Disputes & Chargebacks, Card Activation, Fraud, Merchant Issues, Rewards*

For multi-label cases ("a row may contain multiple requests"), do a first-pass split: ask the LLM to enumerate distinct sub-issues, classify each, then either (a) emit the highest-priority one as the canonical row output and mention the others in `justification`, or (b) escalate if priorities conflict.

### 4.2 Signals for the reply-vs-escalate decision

A robust escalation policy combines **five orthogonal signals**, each contributing a vote:

| Signal | How to compute | When it tips toward escalate |
|---|---|---|
| **Retrieval confidence** | qmd reranker score / wiki page relevance | No matching wiki page above threshold |
| **Topic risk class** | Rule-based regex + LLM tag on `{fraud, lost_card, dispute, chargeback, account_compromise, legal, refund, exam_integrity, payment_failure}` | Any high-risk tag fires |
| **Sentiment / emotion** | Lightweight classifier or LLM tag | Strong negative + threat language ("legal action", "regulator") |
| **Urgency / time-sensitivity** | LLM tag with explicit definition (P0 = service down/financial harm now) | P0 or P1 |
| **PII / identity verification needs** | Regex for card numbers, SSNs, OTPs; presence of "verify my identity" | Always escalate; never echo PII |

A clean implementation: any **single** high-risk topic OR PII match → `escalated`; otherwise score-weighted vote with a tunable threshold. Tune against `sample_support_issues.csv`.

> **LLM Wiki bonus:** During ingest, the wiki pages themselves can be tagged with their escalation risk level (e.g., `escalation_risk: high` in the page frontmatter). This makes the topic risk classification nearly free at query time — you read the page's metadata rather than re-classifying from scratch.

### 4.3 The "invalid" and out-of-scope cases

- Empty / pure noise / prompt injection attempt → `request_type=invalid`, `status=replied` with a polite "out of scope" response. Do **not** escalate.
- Genuine but cross-domain when `company=None` → run qmd search across all three wiki indexes; pick the strongest match if relevance crosses threshold; otherwise escalate.
- Off-topic but real → reply with scope clarification, do not escalate.

The contest rewards agents that **distinguish "out of scope, reply" from "sensitive, escalate"** — a major differentiator.

## 5. Terminal-Based Agent Architecture: Lessons from Claude Code & OpenClaw

### 5.1 Claude Code internals (reverse-engineered)

Multiple reverse-engineering efforts converge on the same architecture:

- **Core: a single async generator query loop** — streams a model response, collects tool calls, executes them, appends results to message history, and loops. Only ~1.6% of the codebase is AI decision logic; 98.4% is deterministic infrastructure — permission gates, context management, tool routing, recovery.
- **Tool system as capability primitives.** Read, Write, Edit, Bash, Glob, Grep, WebFetch, Task (sub-agent dispatch). The model composes primitives instead of reaching for bespoke integrations.
- **Memory:** `CLAUDE.md` / `AGENTS.md` hierarchy — the LLM Wiki schema document lives here.
- **Dual-model usage**: Sonnet for reasoning, Haiku for cheap classification like topic-detection of the user's first message (and for LLM Wiki ingest).

### 5.2 OpenClaw and the "Claw" ecosystem

`github.com/openclaw/openclaw` (Peter Steinberger, Nov 2025) is a general-purpose personal AI assistant gateway connecting messaging platforms to LLMs. Architecture: gateway control plane + per-channel adapters + skills system (ClawHub registry). Spinoffs worth knowing: `moazbuilds/claudeclaw`, `qwibitai/nanoclaw` (container-isolated, Anthropic Agent SDK based), `Enderfga/openclaw-claude-code` (multi-engine ISession abstraction over Claude Code, Codex, Gemini, Cursor Agent).

**What to copy for the hackathon:** the **single async generator loop**, **tool-as-primitive** pattern, **structured streaming**, **explicit termination union**, **per-call permission/risk check before any side-effect**, and **AGENTS.md as the authoritative schema** (which doubles as the LLM Wiki schema document).

### 5.3 Concrete terminal architecture

- `--ticket "..."` — single ticket, interactive

- `--ingest` — trigger the wiki ingest phase (run once before batch)

**Logging:** structured JSONL events (`event=ingest_page`, `event=classify`, `event=wiki_lookup`, `event=qmd_search`, `event=decision`) so the AI Judge can be walked through any decision.

## 6. Failure Modes in Existing Triage AI — and How to Beat Them

| Failure mode | Why it happens | Mitigation (with LLM Wiki) |
|---|---|---|
| **Hallucinated policies** | LLM falls back to training data when retrieval is weak | Every claim in `response` backed by a named wiki page + source URL; AI Judge can verify directly |
| **Cross-domain confusion** | Single shared index; no domain gating | Per-domain `wiki/` directories + domain-conditional index.md lookup |
| **Over-escalation** | No threshold tuning | Calibrate against `sample_support_issues.csv`; wiki page risk tags reduce false positives |
| **Under-escalation on sensitive cases** | No risk taxonomy | Hard-coded high-risk topic list + escalation risk tags pre-embedded in wiki page frontmatter during ingest |
| **Prompt injection from ticket body** | Treating untrusted input as instructions | Wrap user content in delimiters; system prompt treats `<ticket>` as data only; pre-classifier for injection patterns |
| **PII echo** | No output filter | Regex-strip card numbers, OTPs, government IDs from both input and output |
| **Schema drift** | LLM creativity | Pydantic + JSON schema mode; validate and retry once on failure |
| **Multi-request rows handled as one** | Single-pass classification | Decomposition step enumerates atomic sub-issues first |
| **Latency blowup in batch mode** | Calling Sonnet for everything | Haiku for ingest + index.md lookup; Sonnet only for grounded generation when `status=replied` |
| **Justification that just paraphrases response** | Lazy prompting | Force `justification` to cite wiki page name + source URL + the specific signal that drove the decision |
| **Re-synthesis cost on every ticket** | Standard RAG architecture | LLM Wiki: synthesis done once at ingest; query time reads pre-compiled pages only |

## 7. What Differentiates a Winning Submission

A baseline submission: loads raw HTML, chunks, embeds, does dense-only top-k, prompts LLM with ticket and chunks, parses JSON, writes CSV. Will hallucinate, miss Visa fraud escalations, confuse domains on `company=None`.

A **winning** submission layers in, in priority order:

1. **LLM Wiki pre-compilation** — corpus → structured `wiki/` directories with cited, cross-referenced pages and escalation risk tags in frontmatter. The single biggest differentiator vs. naive RAG.
2. **Per-domain `index.md`** — fast first-pass lookup before any search; the triage agent reads the index to identify the 1–3 relevant pages in one LLM call.
3. **qmd for cross-domain / ambiguous tickets** — hybrid BM25+vector search over wiki pages with LLM reranking; replaces FAISS + cross-encoder stack; simpler, same quality.
4. **A typed StateGraph** (LangGraph) so each node is independently inspectable and the AI Judge can be walked through it visually.
5. **Calibrated escalation policy** with multi-signal vote (risk taxonomy from wiki frontmatter + retrieval confidence + PII + sentiment + urgency), tuned against the sample CSV. Show calibration in README.
6. **Groundedness validation** — every sentence in `response` backed by a named wiki page; if not, rewrite or escalate.
7. **Decomposition for multi-request rows.** Most teams won't bother; the rubric explicitly calls this case out.
8. **Cross-domain handling for `company=None`**: qmd search across all three wiki indexes; reranker picks the winner; escalate if no domain crosses threshold.
9. **Prompt-injection and PII hygiene** at both input and output boundaries.
10. **Polished terminal UX**: streaming responses, colored status (green=replied, yellow=escalated), per-row spinner, Rich-formatted summary table at the end (`replied: 73 | escalated: 27 | invalid: 4`), `--repl` mode the judge can play with live.
11. **Honest evaluation report** in README with confusion matrices for `request_type` and `status`, wiki page retrieval recall on labeled queries, and an explicit list of failure cases and why they failed.

## 8. 24-Hour Build Schedule

| Hours | Task |
|---|---|
| **0–3** | Corpus download, `raw/` setup. Run LLM Wiki ingest (Haiku) → `wiki/{domain}/` + `index.md` per domain. Sanity-check 10 pages manually. |
| **3–6** | LangGraph skeleton: sanitize → classify → index.md lookup → qmd search → read wiki pages → ground → validate → write. Pydantic schemas, structured outputs. |
| **6–10** | Escalation policy (5-signal vote, wiki frontmatter risk tags). Groundedness check. Tune thresholds against `sample_support_issues.csv`. |
| **10–14** | Terminal UX (Rich), `--csv` batch mode, `--repl`, `--ingest`, JSONL logging → `log.txt`. |
| **14–18** | Robustness: prompt injection, PII, multi-request decomposition, `company=None` cross-domain qmd search. |
| **18–22** | Evaluation harness, confusion matrices, README with architecture diagram and decision rationale. |
| **22–24** | Final batch run on `support_issues.csv`, transcript cleanup, zip and submit. |
